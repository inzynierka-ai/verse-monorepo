The atom: an LLM call

Every AI app is built from these.

  • System message — role, rules, format
  • User message — the actual request
  • Model, temperature, max_tokens
  • Tools (optional) — function schemas
  • Output: text, structured JSON, or a tool call
response = await client.chat.completions.create(
  model="gpt-4.1-mini",
  messages=[
    {"role": "system",
     "content": "You are a character designer..."},
    {"role": "user",
     "content": "Story: cyberpunk... Describe: a hacker"}
  ],
  temperature=0.7,
  tools=[generate_location, generate_character],
)

Two shapes for AI systems

Workflow

A fixed pipeline of LLM calls. You design each step.

  • Predictable, testable, cheap to debug
  • Good when you know the steps in advance
  • In Verse: character & location generation
Agent

An LLM loop that chooses which tool to call next, until done.

  • Flexible, handles open-ended tasks
  • Harder to predict, debug, and bound in cost
  • In Verse: scene generation

Industry trend: moving toward agents — but you pay for it in complexity.

The agent loop, demystified

while not scene_complete and step < MAX_STEPS:
    response = await llm.generate_response(
        input_text=user_prompt,
        instructions=system_prompt,
        tools=self.tools,            # location, character, finalize
        model=ModelName.GPT41,
    )
    calls = extract_function_calls(response)

    for call in calls:
        if call.name == "generate_location":
            await handle_location(call.arguments)   # → workflow
        elif call.name == "generate_character":
            await handle_character(call.arguments)  # → workflow
        elif call.name == "finalize_scene":
            scene_complete = True

    user_prompt = render_state(self.state)   # feed back the new state

An agent is just a while loop + tools + state.

Use an agent where flexibility matters. Use a workflow where determinism matters. Nest them.

Model choice: don't reach for the biggest

Match model to the difficulty of the step, not the importance of the app.

TaskModel usedWhy
Scene agent (planning + tool use) gpt-4.1 Needs reasoning & tool selection
NPC conversation gpt-4.1 Voice consistency, long context
Character JSON extraction gpt-4.1-mini Structured, well-defined task
Character draft from description gemini-2.0-flash-lite Tiny, templated task — fast & cheap

Rule of thumb: 5–10× cost difference between tiers. Downshift wherever you can.

Prompt engineering: structure beats cleverness

  • Role first — "You are a scene generator..."
  • Tagged sections — <persistence>, <planning>, <tool_usage>
  • Explicit format — "Return only valid JSON"
  • Concrete constraints — "1-3 characters", "250–300 words"
  • Negative rules — "NEVER modify the player character"
<persistence>
Keep going until the scene is
complete. Only terminate when you
have a location, 1-3 characters,
and a description.
</persistence>

<planning>
Plan before each action. Think
about how this scene connects to
previous scenes...
</planning>

Prompt caching: free latency & cost wins

Providers cache the prefix of your prompt. If it matches across requests, you get ≈ 50–90% discount on those tokens and lower latency.

flowchart LR
  A["STATIC prefix — system prompt · tools · few-shot"] --> B["SEMI-STATIC — story · character info"] --> C["DYNAMIC — latest user message"]
  A -.cacheable.-> CACHE[("provider cache")]

  • Put constant content first (system prompt, tool schemas)
  • Then slowly-changing context (story, character)
  • Put the volatile user turn last
  • Don't shuffle keys or timestamps into the prefix

Why NPCs need RAG

Problem:

An NPC in scene #7 should remember what happened with the player in scene #2.

Naive approach: stuff everything into the prompt. Breaks fast — cost & context window.

Solution: RAG

Retrieval-Augmented Generation.

Only retrieve the relevant past memories and inject them into the prompt at response time.

What is an embedding?

A vector (~1536 floats) that captures meaning. Similar texts → close vectors.

Three semantic neighborhoods in vector space: medieval · sci-fi · wilderness.

Langfuse: one decorator, full trace

@observe(name="generate_completion", as_type="generation")
async def generate_completion(self, messages, model, temperature, ...):
    langfuse_context.update_current_trace(metadata={
        "model": model.model_id,
        "provider": model.provider.value,
        "temperature": temperature,
    })
    response = await client.chat.completions.create(...)
    langfuse_context.update_current_observation(usage=response.usage)
    return response.choices[0].message.content

Nested @observe calls build a tree. generate_scene → agent_loop → generate_location → generate_completion.

What a trace actually contains

Per LLM call
  • Model & provider
  • Input messages & system prompt
  • Output text / tool calls
  • Prompt / completion / total tokens
  • Duration
  • Errors, warnings (e.g. moderation)
Per session / trace
  • User / session ID
  • Full nested tree of calls
  • Aggregate cost
  • Custom metadata (step, violated_categories, ...)
  • Scores (manual or LLM-as-judge)

Result: one "bad scene" bug → trace view → exact tool call → exact prompt that caused it.

Takeaways

  1. Start from the atom. An AI app is just LLM calls composed with code.
  2. Workflows first. Reach for agents only when the problem is genuinely open-ended.
  3. Agents = loop + tools + state. Put the rails on your side: max steps, validation, typed state.
  4. Give LLMs memory with RAG. Embeddings + vector DB > stuffing context.
  5. Instrument everything. Langfuse (or equivalent) from day one.
  6. Pick models per task. 80% of your calls probably don't need the flagship.
  7. Structure your prompts — and structure them so they cache.
